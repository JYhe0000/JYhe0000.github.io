# 摘要

2026 年出现的多个开源实验项目，展示了在非 Apple 手机上启动 Apple XNU 内核，并运行来自 iPhone 固件的 iOS 用户空间的可能性。这类项目常被媒体概括为“安卓刷 iOS”，但从工程角度看，它们并不是把一份完整、通用的 iOS ROM 刷入任意 Android 手机，而是针对特定 SoC 和设备，移植 XNU 启动环境、编写硬件驱动，再使用研究者自行取得的 Apple 固件构建系统根文件系统。

其基本链路是：

设备原有 Boot ROM/Bootloader → 自定义 Shim/加载器 → 经修改的 XNU → iOS 根文件系统 → launchd 与系统服务 → backboardd/SpringBoard。

关键突破不在于“ARM 能运行 ARM”，而在于解决不同设备的启动协议、异常级别、内存映射、设备树、CPU 多核启动、中断控制器、计时器、存储控制器、显示与输入设备等问题。CPU 指令集相同只是必要条件之一，绝不是驱动和系统 ABI 自动兼容的保证。

截至本报告日期，HakiOS/HackiOS、ios-sweet、PixOS、Scion 等项目已经提供了不同程度的实机或虚拟化验证。但不同项目、不同设备、不同系统版本的完成度差异很大；能进入桌面并不等于具备电话、蜂窝数据、蓝牙、完整 GPU 加速、Apple 服务和可靠安全机制。它们仍属于研究性移植，不应视为可日常使用的 iOS ROM。

# 1. 术语与范围界定

# 1.1 “安卓刷 iOS”实际可能指什么

网络上“安卓刷 iOS”至少包含四种完全不同的技术路线：

路线 实际含义 是否为原生 iOS
iOS 风格桌面/主题 Android Launcher、图标包、控制中心仿制 否
iOS 应用兼容层或模拟器 在 Android/Linux 上模拟或转译部分 iOS API/指令 通常否
虚拟机运行 在 Android Hypervisor 或 QEMU 中启动经过适配的系统 客体系统可以是真实 Darwin/iOS 用户空间，但不是裸机启动
裸机 XNU 移植 设备加载适配后的 XNU，再启动 iOS 用户空间 属于真正的内核/系统移植实验

本文重点讨论后两种，尤其是 Android 手机硬件直接运行 XNU 的路线。

# 1.2 XNU、Darwin 与 iOS 的关系

  • XNU：Apple 操作系统使用的内核，名称通常解释为“X is Not Unix”。它结合 Mach、BSD 子系统以及 IOKit 等机制。
  • Darwin：Apple 操作系统的底层基础系统，包含 XNU、BSD 用户空间组件及相关基础设施。
  • iOS：建立在 Darwin 之上的完整移动操作系统，包含专有系统框架、守护进程、图形栈、安全机制和应用。
  • SpringBoard：iOS 主屏幕与应用启动界面的核心进程之一。
  • launchd：系统启动和服务管理的核心进程。

Apple 公开发布了 XNU 的部分源代码，但这不代表完整 iOS 开源。UIKit、SpringBoard、系统服务、部分驱动、固件和安全组件仍然具有专有属性。开源内核可以被移植，不等于开发者因此获得了完整 iOS 的源码或再分发权。

# 2. Android 与 iOS 的底层架构差异

# 2.1 Android 典型软件栈

┌──────────────────────────────────────┐
│ Android Applications                 │
├──────────────────────────────────────┤
│ Android Framework                    │
│ Activity / Window / Package / System │
├──────────────────────────────────────┤
│ Android Runtime                      │
│ ART / Core Libraries                 │
├──────────────────────────────────────┤
│ Native Libraries / HAL               │
│ Bionic / EGL / Vulkan / Hardware HAL │
├──────────────────────────────────────┤
│ Linux Kernel                         │
│ Scheduler / VM / VFS / Drivers       │
├──────────────────────────────────────┤
│ SoC / RAM / UFS / Display / Peripherals│
└──────────────────────────────────────┘

Android 的 Linux 内核负责进程调度、虚拟内存、设备中断、文件系统和驱动等基础功能。Android Framework、ART、Bionic、HAL 等组件构成其上层运行环境。

# 2.2 iOS 典型软件栈

┌──────────────────────────────────────┐
│ iOS Applications                     │
│ UIKit / Swift / Objective-C           │
├──────────────────────────────────────┤
│ Apple System Frameworks              │
│ Foundation / CoreFoundation / etc.   │
├──────────────────────────────────────┤
│ System Services                      │
│ SpringBoard / backboardd / other daemons│
├──────────────────────────────────────┤
│ Darwin User Space                    │
│ launchd / libSystem / BSD interfaces │
├──────────────────────────────────────┤
│ XNU Kernel                           │
│ Mach + BSD + IOKit                   │
├──────────────────────────────────────┤
│ SoC / RAM / NAND or UFS / Peripherals│
└──────────────────────────────────────┘

两者的核心差别不是“一个是 ARM、另一个也是 ARM”，而是内核接口、启动协议、驱动模型、系统调用、用户空间 ABI、图形与安全框架均不相同。

# 2.3 XNU 的组成

XNU 并非简单的 Linux 替代品，主要包含：

  1. Mach 层：任务与线程抽象、IPC、虚拟内存基础机制、调度相关机制。
  2. BSD 层：POSIX 接口、进程与用户身份、网络协议栈、文件系统及传统 Unix 语义。
  3. IOKit：Apple 的设备驱动框架，采用面向对象的驱动模型。
  4. 平台与架构代码：处理器初始化、中断、计时器、缓存、异常和平台相关功能。

Android 的 Linux 驱动不能直接作为 XNU/IOKit 驱动使用。即便两边都控制同一颗 UFS、GPU 或触摸控制器，也需要编写适合目标内核的驱动，或通过专门的适配层提供等效服务。

# 3. 核心启动链：从 Android Bootloader 到 XNU

# 3.1 原生 Android 启动流程

典型 Android 启动过程可抽象为：

上电
  ↓
Boot ROM
  ↓
SoC 厂商早期启动固件
  ↓
Bootloader（如 Qualcomm ABL / Samsung S-Boot）
  ↓
Android Boot Image / Vendor Boot
  ↓
Linux Kernel + Device Tree
  ↓
init
  ↓
Android Native Services
  ↓
Zygote / System Server
  ↓
Android Framework / Launcher

具体启动阶段会因 SoC 厂商、设备代际、A/B 分区、AVB 和厂商启动链而变化。

# 3.2 裸机 XNU 移植的启动流程

实验项目通常保留设备原有 Boot ROM 与 Bootloader，再通过解锁后的启动链加载自定义程序：

上电
  ↓
Boot ROM
  ↓
设备原有 Bootloader
  ↓
自定义 Shim / EFI Loader
  ├─ 初始化或接管必要硬件状态
  ├─ 建立内存映射
  ├─ 整理启动参数与设备描述
  ├─ 准备内核映像和根文件系统信息
  └─ 跳转到 XNU 入口
        ↓
    Patch 后的 XNU
        ↓
    BSD / IOKit 初始化
        ↓
    挂载 iOS 根文件系统
        ↓
    launchd
        ↓
    系统守护进程
        ↓
    backboardd / 图形服务
        ↓
    SpringBoard

这里的 Shim 是位于固件启动链与 XNU 之间的薄层启动程序。它不是 Android，也不是 iOS 本身，而是负责把目标设备当前的硬件状态整理成 XNU 能理解的启动环境。

有的项目采用 UEFI 风格加载器，有的使用更精简的自定义启动代码；不能把所有项目都描述成同一种 UEFI 实现。

# 3.3 为什么不能直接把 XNU 内核写入 boot 分区

Android Boot Image 与 XNU 所期望的启动环境并不天然兼容。Android 内核通常由设备启动固件按照厂商约定传入参数、设备树和 ramdisk；XNU 则需要自身可识别的启动参数、平台描述、内存布局和启动状态。

因此，移植者需要解决：

  • 内核映像格式与加载地址；
  • CPU 当前异常级别和执行状态；
  • MMU、页表及缓存状态；
  • 内存区域与保留内存；
  • 中断控制器与计时器；
  • 设备树或 Apple Device Tree（ADT）信息；
  • 根文件系统位置和挂载方式；
  • 从固件交接给内核时的寄存器与参数约定。

Shim 的价值就是把这些差异隔离在内核之前，使 XNU 不必从零开始理解每一家 Android 手机的启动固件。

# 3.4 RAM 启动与真正刷写的区别

部分项目使用类似 fastboot boot 的临时启动方式，把 Shim 或启动映像加载到 RAM，而不直接覆盖设备的 Boot 分区。

这种模式的优点是：

  • 原有 Bootloader 通常仍然保留；
  • 重启后可以重新进入原有 Android 启动路径；
  • 降低改写启动分区造成的风险；
  • 便于反复调试启动程序和内核。

但“从 RAM 启动”不代表完全无风险。项目仍可能格式化或占用 userdata 分区存放 iOS 根文件系统，也可能修改分区布局、文件系统或设备状态。必须以具体项目的安装说明为准。

# 4. ARM64 兼容性：同为 ARM 不代表可以直接运行

# 4.1 指令集只是第一道门槛

大多数现代 Android 手机使用 ARM64，但不同 SoC 的实现存在差异：

  • Cortex-A 系列核心型号不同；
  • ARMv8.x / ARMv9 特性支持不同；
  • 页大小可能为 4 KB 或 16 KB；
  • 是否支持 Pointer Authentication（PAC）不同；
  • GIC 中断控制器版本不同；
  • PSCI、SMC、固件调用约定不同；
  • 缓存一致性、定时器和电源管理实现不同。

因此，“同为 ARM64”只说明存在一定的指令集基础，并不意味着 iPhone 内核能直接在 Snapdragon、Exynos、Tensor 或 MediaTek 平台上启动。

# 4.2 CPU 多核启动

XNU 必须正确发现并启动 CPU 核心。Android 设备通常依靠 PSCI 等固件接口启动次级 CPU 核心，移植工程需要处理：

  • CPU 拓扑识别；
  • 主核与次级核启动；
  • 每核栈和异常向量；
  • TLB 与缓存维护；
  • 自旋锁与跨核同步；
  • 调度器初始化；
  • 核心频率与电源状态。

如果只启动一个核心，系统可能能够进入早期内核阶段，但性能和功能会受到限制。多核启动错误还可能导致死锁、随机崩溃或启动阶段卡死。

# 4.3 内存管理与页大小

不同平台的内存布局并不统一。移植者必须确认：

  • DRAM 实际物理地址范围；
  • Bootloader 保留的内存区域；
  • 固件、TrustZone、modem 等 carve-out；
  • 内核映像与 ramdisk 的加载地址；
  • 页表格式与页大小；
  • 物理内存映射和 DMA 可访问区域；
  • 缓存属性及设备内存映射。

如果 XNU 对页大小、物理地址或保留内存的假设与设备不一致，可能在极早期就发生异常。

# 4.4 中断控制器与计时器

中断和计时器是内核运行的基础设施。

ARM 手机通常使用 GIC（Generic Interrupt Controller）管理中断，系统计时则依赖架构定时器或平台计时源。移植者需要让 XNU 正确处理：

  • IRQ 与 FIQ；
  • 中断优先级和屏蔽；
  • 每 CPU 中断状态；
  • 系统时钟；
  • 调度时钟 tick；
  • 超时、睡眠与唤醒；
  • IPI（处理器间中断）。

没有可靠的中断和计时器，系统即使打印出内核启动日志，也无法稳定运行调度器和设备驱动。

# 5. 设备树、硬件描述与驱动适配

# 5.1 设备树的作用

Linux Android 平台通常使用 Device Tree（DT/DTB）描述硬件资源，例如：

  • CPU 节点与拓扑；
  • 内存区域；
  • 中断控制器；
  • UART；
  • I²C / SPI 控制器；
  • UFS 控制器；
  • GPIO；
  • 显示控制器；
  • 电源管理与时钟资源。

Apple 平台使用 Apple Device Tree（ADT）等平台描述机制。将 Linux DTB 原样交给 XNU 并不能解决问题，因为两者的数据格式、属性语义和驱动查找方式并不相同。

因此，移植者需要构建或转换一份 XNU 能识别的平台描述，并确保地址、中断号、时钟、复位线和电源域信息准确。

# 5.2 驱动移植不是复制文件

Linux 驱动与 IOKit 驱动的接口、生命周期和资源管理方式不同。移植时通常需要重新实现驱动，或编写适配层。

硬件模块 主要工作 难点
UFS 存储 控制器初始化、命令队列、读写、错误恢复 厂商差异、启动固件状态
显示面板 framebuffer、分辨率、刷新率、背光 DSI 初始化、时序、电源域
触摸屏 I²C/SPI、输入事件、坐标映射 中断、手势、多点触控
GPU 内存管理、命令提交、图形 API 固件、提交队列、用户态驱动
Wi-Fi 总线、固件加载、网络接口 固件依赖、校准数据、协议栈接口
蓝牙 UART/USB、控制器固件、协议栈 HCI、共存与电源管理
音频 Codec、DSP、路由和时钟 厂商 DSP、音频拓扑
摄像头 Sensor、ISP、时钟、数据通路 ISP 固件、HAL 与专有协议
电源管理 PMIC、充电、温控、DVFS 安全固件、热管理策略
蜂窝基带 Modem、RIL 类接口、SIM 与网络服务 专有协议、认证和系统服务

驱动可用程度决定了系统从“能够启动”到“能够使用”的差距。

# 6. iOS 用户空间如何在非 Apple 硬件上运行

# 6.1 内核启动不等于 iOS 桌面启动

XNU 成功启动，只能证明内核早期初始化和部分平台支持已经工作。要进入 iOS 桌面，还必须提供兼容的用户空间：

  1. 可读写的系统根文件系统；
  2. 正确的动态链接器和系统库；
  3. launchd；
  4. 必要的系统守护进程；
  5. 图形与输入服务；
  6. SpringBoard 及其依赖框架。

项目通常使用与目标 XNU 版本相匹配的 iOS 固件用户空间。版本不匹配可能导致系统调用、内核接口、驱动接口或私有框架行为不一致。

# 6.2 启动过程

典型用户空间启动链可简化为：

XNU 完成内核初始化
       ↓
BSD 子系统初始化
       ↓
挂载根文件系统
       ↓
launchd（PID 1）
       ↓
系统守护进程与服务
       ↓
图形、显示、输入相关服务
       ↓
backboardd 等图形服务
       ↓
SpringBoard
       ↓
锁屏与主屏幕

不同 iOS 版本的服务依赖关系会变化，实际启动链不应被理解为所有版本完全固定的线性列表。

# 6.3 为什么有时能看到 iOS 桌面，却不能正常使用

SpringBoard 出现只代表部分关键路径已经成功：

  • 内核能够运行；
  • 根文件系统能够读取；
  • launchd 能启动；
  • 关键系统服务能工作；
  • 显示路径至少有一种方式可用。

它并不证明电话、短信、蜂窝网络、蓝牙、相机、硬件编解码、Apple ID、App Store、iCloud、支付和安全隔离都正常。

# 7. 图形系统：从 framebuffer 到 GPU 与 Metal

# 7.1 最低限度的显示输出

最初阶段可以使用 Bootloader 留下的 framebuffer，将 CPU 绘制的图像写入屏幕缓冲区。

这条路径相对简单，但通常存在：

  • CPU 绘制负担高；
  • 分辨率或刷新率受限；
  • 缺少硬件合成；
  • 动画和滚动性能较差；
  • 显示方向、亮度与休眠控制不完整。

# 7.2 GPU 加速的复杂性

GPU 不只是一个“能画图”的设备。完整支持通常涉及：

  • GPU 内存管理；
  • 命令缓冲区与提交队列；
  • 中断和同步原语；
  • 固件加载；
  • 缓存一致性；
  • 用户态图形驱动；
  • Window Server / CoreAnimation 的接口；
  • 图形 API 与着色器编译。

# 7.3 Metal 的含义

Metal 是 Apple 的图形与计算 API。项目展示 GPU 绘制或 Metal 相关成果时，必须区分：

  • 仅使用 framebuffer 输出；
  • 由 CPU 软件渲染；
  • 使用 Mesa 等组件提供 OpenGL ES/Vulkan 路径；
  • 实现足以支持特定系统图形路径的 Metal 兼容层或驱动。

“GPU 能显示桌面”并不自动等于完整 Metal 兼容，更不等于所有 iOS 游戏和应用都能正常运行。

# 8. 安全机制：为什么能启动不代表安全模型完整

iOS 的安全模型涉及多个硬件与软件层次：

  • Secure Boot 与启动链信任；
  • AMFI（Apple Mobile File Integrity）；
  • 代码签名与 entitlement；
  • 沙盒与访问控制；
  • 数据保护与密钥管理；
  • Secure Enclave（SEP）；
  • 基带与设备身份相关机制；
  • Apple 服务端的设备认证。

Android 手机并没有与 iPhone 完全相同的 Apple 安全硬件和固件环境。因此，移植项目可能需要关闭、绕过、替换或 stub 某些安全检查，才能让非 Apple 平台上的用户空间继续运行。

这会产生两个重要后果：

  1. 系统可能无法提供原生 iPhone 等级的数据保护与应用隔离。
  2. Apple ID、iMessage、FaceTime、Apple Pay、iCloud、App Store 等服务不因桌面启动成功而自动可用。

特别需要强调：能够运行 iOS 用户空间，不等于设备已经通过 Apple 的硬件身份认证，也不等于能够伪装成一台受支持的 iPhone。

# 9. 代表性项目与技术路线

以下状态以项目公开文档在 2026-11-24 前可查到的记录为准。项目更新频繁，实机状态应以对应仓库的最新提交、设备记录和可复现日志为准。

# 9.1 HakiOS / HackiOS

  • 项目：https://github.com/oosexgang/hakios-xnu-kernel
  • 主要方向：面向 Android 手机移植 XNU，提供自身的加载器、驱动和构建工具。
  • 代表设备：POCO X5 Pro 5G（Snapdragon 778G / Adreno 642L）。
  • 公开成果：项目说明了 XNU 在目标设备上的启动，以及触控、显示、Wi-Fi、音频、相机和 Adreno GPU 图形路径等进展。
  • 技术特点：强调设备端裸机运行和独立驱动；部分实现能够从 RAM 启动，重启后回到原系统启动路径。
  • 限制：项目仍是研究环境；硬件功能完成度、系统服务和安全机制不能与原生 iPhone 等同。

# 9.2 ios-sweet

  • 项目：https://github.com/dipa-studio/ios-sweet
  • 代表设备：Xiaomi Redmi Note 10 Pro（代号 sweet，Snapdragon 732G / SM7150）。
  • 系统用户空间：项目文档记录使用 iPhone X 的 iOS 16.7.16 用户空间。
  • 公开成果：XNU 启动、部分 CPU 核心、UFS 存储、触控、显示、launchd、SpringBoard 等路径。
  • 技术特点：通过设备专用 Shim 启动经过修改的 XNU，并从用户数据分区挂载 iOS 根文件系统。
  • 限制：项目明确属于实验性移植；文档记录其安全模型大量关闭或替代，且早期图形路径主要依靠 CPU 软件渲染。

# 9.3 PixOS

  • 项目主页：https://pixos-project.github.io/pixelios-site/
  • 代表设备：Google Pixel 6a（Tensor G1）。
  • 技术基础：以 ios-sweet 的移植工作为基础，进一步适配 Tensor 平台。
  • 公开成果：Shim、XNU、iOS 16 用户空间、触控与桌面启动等阶段性实机记录。
  • 技术特点：文档将启动链、设备树、CPU、UFS、显示、GPU、触控、Wi-Fi 等工作拆成可验证的移植阶段。
  • 限制：项目自述为研究移植，不是日常使用系统；不同外设的状态必须按组件文档分别核对。

# 9.4 Scion

  • 项目主页：https://scion-project.github.io/
  • 项目源码：https://github.com/cooblg/scion-kernel
  • 代表设备：Samsung Galaxy S9（Exynos 9810），并有其他设备和虚拟化路线的开发。
  • 公开成果：项目记录 Galaxy S9 上的 iOS 16.5 与 iOS 27 启动进展，并尝试在一个内核代码树中维护不同 XNU 基线。
  • 特点：强调共享驱动、SoC 层和设备配置，并明确区分实机运行、已构建但未实机运行、尚未实现。
  • 限制：不同设备的启动方式和完成度不相同。Pixel 10 的虚拟机路线不能与 Galaxy S9 裸机路线混为一谈；项目设计中的双启动目标也不能提前当成已完成能力。

# 9.5 项目对比

项目 代表平台 核心路线 用户空间/版本线索 关键注意事项
HakiOS POCO X5 Pro 5G 裸机 XNU 移植 iOS 16 代际相关用户空间 关注其独立驱动与 GPU 进展
ios-sweet Redmi Note 10 Pro 裸机 XNU + Shim iOS 16.7.16 早期图形以 CPU 渲染为主
PixOS Pixel 6a Tensor 平台移植 iOS 16 用户空间 以组件里程碑衡量进度

这些项目不是可以互换的通用 ROM。某个设备上的驱动成果不能直接推导到另一台设备，即使它们都使用 Qualcomm 芯片，也可能因为 SoC、显示面板、PMIC、存储、触控控制器和固件版本不同而无法直接复用。

# 10. 为什么 iOS 16 比更新版本更容易成为移植起点

移植目标版本需要同时考虑 XNU 版本、用户空间版本、CPU 指令集能力和 Apple 安全硬件依赖。

其中一个重要因素是 Pointer Authentication（PAC）。

PAC 是 ARMv8.3-A 等较新架构提供的指针认证能力。较新 Apple 平台和系统版本可能依赖 arm64e 相关能力；老一代 Android SoC 未必具备相同硬件特性。

因此，较旧的 iOS/XNU 版本往往更适合在非 Apple ARM64 平台上进行早期移植研究。但这并不是“所有 iOS 17 以上版本都绝对不能移植”的简单结论：具体取决于目标用户空间、二进制架构、内核配置、硬件特性和项目是否实现了相应兼容方案。

版本匹配至少需要核对：

  1. XNU 源码基线；
  2. iOS 用户空间版本；
  3. Mach-O 二进制架构；
  4. arm64 与 arm64e/PAC 依赖；
  5. 页大小和内存模型；
  6. 私有系统框架与内核接口；
  7. 目标设备硬件能力。

# 11. 从实验桌面到可用手机：功能成熟度分层

可以将项目成熟度分成以下层次：

等级 技术成果 能说明什么
L0 XNU 能执行早期启动代码 启动链与基本 CPU 环境可用
L1 内核初始化、调度器和内存管理正常 基础内核 bring-up 成功
L2 根文件系统挂载、launchd 运行 iOS 用户空间开始运行
L3 显示、触控、SpringBoard 可用 能看到并操作桌面
L4 GPU、Wi-Fi、音频、相机等外设工作 具备部分日常交互能力
L5 蜂窝网络、电话、蓝牙、休眠、充电和功耗管理稳定 接近完整移动设备体验
L6 安全机制、Apple 服务、应用生态与长期稳定性达到可用标准 才可能讨论日常替代 iPhone

上述分层是本文用于分析的工程评价框架，并非任何项目官方发布的等级标准。

目前公开成果主要集中在 L2 至 L4 的不同组合；不能因为某个演示进入主屏幕，就认为已经达到 L5 或 L6。

# 12. 主要工程瓶颈

# 12.1 蜂窝基带与电话服务

手机基带通常由独立固件和专有协议控制。即使 modem 本身仍能在原固件中运行，也需要操作系统侧的接口、服务和设备管理逻辑配合。

可能涉及：

  • SIM 与网络注册；
  • APN 和数据连接；
  • modem IPC；
  • 电话与短信服务；
  • 紧急呼叫；
  • 运营商配置；
  • 基带固件和设备身份认证。

这是桌面演示与真正手机之间最明显的鸿沟之一。

# 12.2 电源、充电与热管理

移动系统必须正确管理 CPU/GPU 频率、温度、休眠、唤醒、充电状态和电池保护。缺少这些能力可能导致：

  • 待机耗电严重；
  • 充电状态不正确；
  • 设备过热；
  • 低电量关机行为异常；
  • 睡眠后无法唤醒；
  • 长时间负载下不稳定。

# 12.3 GPU 与媒体管线

GPU 图形输出只是第一步。视频解码、摄像头 ISP、图像处理、硬件编解码和游戏渲染还涉及大量专有固件和用户态组件。即使桌面动画流畅，也不代表完整媒体能力已经移植。

# 12.4 安全与 Apple 服务

没有 Apple 原生安全硬件环境、设备身份和服务端认证，很多 Apple 服务无法自然工作。通过关闭安全检查让系统启动，也不能被视为真正解决了兼容性问题。

# 13. 可复现性与实验风险

这类项目通常要求解锁 Bootloader，并可能使用 fastboot boot、自定义分区映像或用户数据分区作为系统根文件系统。

实验前至少应确认：

  • 目标设备代号、SoC 和硬件修订版；
  • Bootloader 是否可解锁；
  • 是否有可用的原厂固件和完整恢复路径；
  • 是否备份照片、密钥、账号数据及重要文件；
  • 项目是否会格式化 userdata；
  • 是否修改 boot、vendor_boot、dtbo、vbmeta、super 等分区；
  • 是否有可用的 EDL、Download Mode 或厂商恢复方式；
  • 下载的二进制和脚本是否来自可信仓库。

不要把实验项目的“可启动”理解成“刷入失败也一定能无损恢复”。 特别是会擦除用户数据或改变分区布局的方案，应先在备用设备上验证。

# 14. 未来发展方向

# 14.1 从单设备移植走向平台化

早期移植通常高度依赖某一款手机。未来更有价值的方向是把代码拆分为：

  • 通用 XNU 补丁；
  • SoC 公共驱动；
  • 厂商平台层；
  • 设备专属配置；
  • 启动加载器；
  • 用户空间构建工具；
  • 自动化测试与恢复工具。

如果同一 SoC 家族的多个设备可以复用大部分代码，移植成本才有机会显著下降。

# 14.2 自动化移植与 AI 辅助开发

设备驱动研究涉及寄存器、设备树、固件行为、内核日志和反汇编。AI 编程代理可以帮助分析 Linux 驱动、整理寄存器访问、生成适配代码、追踪编译错误和编写测试。

但 AI 生成代码不等于硬件验证。真正的里程碑仍然必须由实机日志、可重复测试和故障恢复结果证明。

# 14.3 双系统与多启动

保留 Android、通过启动菜单选择不同系统，是一个有吸引力的目标。但要做到安全双启动，需要妥善处理：

  • 分区与文件系统布局；
  • Bootloader 启动项；
  • AVB 与启动链状态；
  • Android 数据分区共享或隔离；
  • 系统更新与恢复；
  • 两套系统对 modem、固件和持久化数据的访问冲突。

“重启后回到 Android”与“已经实现完整双系统”是两件不同的事。

# 15. 结论

所谓“安卓刷 iOS”，真正的技术核心不是把 Android 改造成 iOS，也不是简单地把 iPhone 固件写进安卓手机，而是将 Apple 的 XNU 内核移植到非 Apple ARM 硬件，并构建一套能够启动 iOS 用户空间的硬件适配环境。

整个工程可以归纳为四个层次：

  1. 启动层：利用原有 Boot ROM/Bootloader，通过 Shim 或加载器建立 XNU 所需的启动环境。
  2. 内核层：适配 ARM64、内存管理、CPU 多核、中断、计时器和 XNU 平台代码。
  3. 驱动层：为 UFS、显示、触控、GPU、Wi-Fi、音频、摄像头和电源管理等硬件提供 XNU 可用的驱动。
  4. 用户空间层：使用匹配的 iOS 系统文件，启动 launchd、系统守护进程和 SpringBoard。

这类项目证明了一个重要事实：iOS 的底层系统并非在技术上只能运行于苹果自家的处理器上。 只要指令集、内核、启动环境和硬件驱动得到适配，非 Apple ARM 平台也可以成为 Darwin/XNU 的运行目标。

但这并不意味着 iOS 已经成为可随意安装在安卓手机上的通用操作系统。当前成果仍然受到设备适配、专有驱动、Apple 安全硬件、基带服务和系统生态的限制。

从操作系统研究的角度看，这些项目真正重要的意义，是它们把原本封闭在 Apple 硬件生态中的一部分底层系统技术，变成了可以在第三方 ARM 设备上研究、验证和扩展的工程对象。
